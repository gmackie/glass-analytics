Goals and non-goals

Goals

  • Repeatable onboarding for every eligible ForgeGraph app.
  • Browser, Worker and DO events with explicit person/session or case correlation.
  • Trustworthy, bounded journey queries available to humans and agents.
  • Sankeys that explain branching and observation limits.
  • Enforced education policies and verifiable deletion.
  • Evidence-based Flightdeck cutover and retirement.

Outside the first release

  • Automatic instrumentation of every account resource.
  • Implicit cross-app or cross-district identity joining.
  • Collecting students' free text, conversations or replay by default.
  • Unbounded path enumeration or unexplained sampling.
  • Exactly-once delivery claims without store-level proof.
  • Porting every Flightdeck feature without a consumer.

Contracts to settle before implementation

Event classes, identity and the catalog

Introduce an explicit event class: product for a person's activity, process for case transitions, and operational for system activity. Exact transport fields are proposed; finalize an ADR before changing stored schemas. Do not infer a person from a DO id, Worker name or case id.

  • Person journeys: project + resolved person + session; client-generated correlation may be sent only when permitted. EducateOS identities derive from district + issuer + subject using a tenant-specific keyed pseudonym; emails are not keys. A pseudonym remains protected data.
  • Case journeys: project + process key + case id + definition version. Preserve occurrence time and, when the domain provides one, a source sequence. Person identity is optional and separately authorized.
  • Operational events: app/environment/resource class, event id and bounded measurements. No user identity by default. Provider invocation metrics and product activity are separate signals.
  • Cross-app: off initially. Later use an explicit identity namespace, authorized project set and collection purpose. Never join matching raw ids across projects.
  • Catalog: propose dataflare.events.json in each app repo: schema version, event class, name, description, typed property allowlist, sensitivity, approved labels, correlation requirements, retention class and owner. Exclude secrets and real records. Dataflare stores the published version/digest used to validate events.
  • Migration: default legacy events to product only under documented compatibility rules. The draft helper's case distinct_id + journey_id recipe is provisional; migrate case events before enabling case analytics so they never inflate people/retention counts.

Verification: shared devices, login changes, multiple sessions, reused ids across projects/districts, schema upgrades, unknown events/properties, missing correlation and policy-version changes all have executable fixtures.

Journey query and result semantics

Implement one journeys insight with a bounded portable candidate query and deterministic core reducer first. Benchmark this against a portable SQL adjacency strategy before choosing the production execution plan. Both D1 and Basin must produce the same answers. Avoid mandatory window functions; use dialect helpers for engine differences.

AreaProposed v1 rule
Scope and unitExactly one authorized project. Session journeys first; one eligible session contributes one path. Person journeys across sessions and case journeys are later modes with their own keys, never an ambiguous switch.
AnchorsForward from an event/page, backward toward an event/page, or complete selected sessions. Default first matching anchor per session; additional anchor occurrences require an explicit later mode. Cohort filters select sessions; node/event filters define visible steps. Hidden events connect adjacent visible steps, and the response names that behavior.
OrderingSort by occurrence timestamp then event id. Equal timestamps have deterministic display order, not proven causal order. Case mode uses source sequence/version rules where available; report conflicts and corrections.
Nodes and loopsNormalized approved page templates or catalog event labels. Node identity includes step position, so A → B → A remains a forward layered graph. Optional consecutive-repeat collapse must be explicit. Never use arbitrary student text or raw entity-bearing URL paths as labels.
Range and observationAnchor/cohort interval is [from,to). Retrieve bounded context before/after anchors up to maxDuration, constrained by the source watermark. Label missing prior context and immature trailing observation. Separate observed end, observation pending, step limit, duration limit and excluded/unknown. An observed end is not proof of abandonment.
Counts and pruningLink width counts eligible sessions traversing that transition at that position. Report cohort denominator. Top labels aggregate to Other while preserving flow totals; explicit termination categories conserve counts. Distinct people can overlap across branches and must not be summed as flow.
BudgetsProvisional pilot limits: 10 steps, 10 displayed labels per step, 24-hour duration, 7-day anchor range, 50,000 candidate rows. These are starting caps, not measured capacity. Retrieve N+1 and reject overflow with a useful narrower-query hint; never silently return a partial graph. Use one coherent cutoff/snapshot where supported and disclose completeness/freshness.
ResultSpec/version digest, nodes, edges, denominators, termination categories, SQL used, dashboard URL, summary, query mode, units, as-of/watermark, source freshness, limit/pruning/suppression metadata and a non-causal statement. Restricted education results omit unsafe counts and raw drilldowns.

Performance gate: measure D1 rows scanned/read budget, Basin bytes scanned and feature support, Worker CPU/memory, result size and p50/p95 latency on synthetic skewed workloads. Set release SLOs from those results before increasing caps. If bounded extraction cannot meet them, add portable edge aggregation or a rebuildable summary store with policy/definition/watermark keys; do not add a second unrestricted query path.

Delivery phases and dependencies

Sequence is dependency-based, not a calendar estimate. Every phase ends in a reviewable vertical slice. Product and privacy work proceed independently until a particular app's collection or display gate requires both.

  1. 0. Inventory and decisions → confirmed owners, app list and acceptance map.
  2. 1. Capture pilot and catalog → one app proves the path; common event contracts stabilize.
  3. 2. Journey engine and Sankey → synthetic correctness, agent API and usable dashboard.
  4. 3. Portfolio rollout and delivery reliability → waves of apps, with outboxes for required events.
  5. E. Education privacy, in parallel → district boundary, enforced controls and verified erasure before students.
  6. 4. Lifecycle migration and Flightdeck retirement → verified replacements, cutover, then archival.
